Four times the machines caught us

A verification story you should trust will include the failures. Ours has three, each found by finally making a machine touch a claim that had only ever lived in prose.

  1. The TLA+ specs had never parsed. The coverage doc said "model-checked by TLC"; the first real TLC run rejected every file on syntax. Fixing the syntax surfaced three genuine state-machine bugs in the Elm — all fixed in 1.2.1, and TLC now runs in CI so the claim can never silently rot again.
  2. The Lean proofs verified a typo. decodeRevertReason compared reverts against selector 08c379a2; the real Error(string) selector is 08c379a0. The proofs were sound — about the wrong constant — so no real revert reason ever decoded. A rendered payload in the gallery exposed it in one frame; fixed in 1.2.2 and pinned by canonical solc vectors. Proofs guarantee internal consistency; constants that point at the world need oracle tests against the world.
  3. Three "proved" statements were false. Repairing the files forced the checker's eye onto every statement, and three did not survive it: the BigInt subtraction lemma admitted invalid digit lists (a=[], b=[-5] satisfies its hypothesis and refutes its conclusion), and both revert-decoder guard theorems stripped the 0x prefix unconditionally where the code strips it conditionally. All three are quarantined in the files with their counterexamples — a false claim gets recorded, not silently reworded.
  4. Seven of ten Lean files had never compiled. The first local lean run (2026-07-02) checked three files clean and rejected seven with 86 errors. Fifteen "Proved" rows were downgraded to "authored, unverified" the same hour, and are promoted back one file at a time as the checker — not the author — says so.

The pattern is the point: every grade in the ledger is now backed by a command you can run and CI re-runs on every change.
